Single most important structural finding: the Design System package and the Portal application are two entirely separate codebases that are not wired together. A repo-wide grep for @core-ds across both Portal branches returns zero hits — the Portal never imports @core-ds/core, @core-ds/tokens, or @core-ds/themes. The Portal has its own hand-written CSS token system (src/styles/index.css, plus core-color-palette.css on journey-retirement) that in places manually copies specific hex values from the Design System's Figma export (e.g. the shared brand navy #1F4F8D appears in both), but this is a one-time manual value-sync, not a structural dependency. Any future Design System change (a token, a component fix, an accessibility correction) will not propagate to the Portal automatically — see Reconciliation.

Design System status

The token architecture is real (a genuine primitives → semantic → component JSON pipeline that builds cleanly) but is undermined by a second, hand-maintained --theme-* CSS variable set that the actual component stylesheet depends on more than the generated one, 236 raw hex literals (several with no token fallback at all), a broken out-of-the-box dev workflow, and — the most consequential single defect — 4 of 6 semantic button tones (destructive, success, warning, info) fail WCAG AA contrast for white-on-color text, with warning failing even the large-text floor (2.32:1). Structural accessibility (ARIA roles, focus management, keyboard semantics) is strong. The documentation site itself has no usable navigation below ~1024px width.

Portal status — main

Functionally solid across the great majority of flows (14 of 17 exercised flows WORKING). Two high-visibility, demo-breaking bugs found: the Investment Portfolio page shows identical, hardcoded figures regardless of which participant is logged in, and the enrollment flow displays a hardcoded placeholder plan name ("401(k) Company Plan High Returns") instead of the real plan. A real mobile layout bug was confirmed via DOM coordinates: a floating "Prototype demo" button overlaps two bottom-nav tabs at 375px width. 7 dead component files and 3 parallel app-chrome implementations add maintenance risk. No automated tests.

Portal status — journey-retirement

Same core architecture as main, plus 5 additional commits focused on portfolio/plan-table mobile-card responsiveness — those specific fixes hold up cleanly at all three tested viewports. The same Investment Portfolio non-participant-aware bug and the same hardcoded enrollment plan-name bug are present here too (this is shared, upstream-of-both-branches code, not something introduced by either branch). Two new findings specific to this branch: a real, reproduced timezone off-by-one bug in the shared DatePicker component, and a stale PROJECT_NOTES.md that describes a teal/forest "Journey Retirement" re-skin which does not exist anywhere in this branch's actual code (it runs LendGuard/CORE-Blue branding instead) — meaning the branch's own documentation misrepresents its current state.

Design System — Overview & Provenance

  • Product: "CORE Design System" for a fictional 401(k) recordkeeping platform, an npm-workspaces monorepo (packages/tokens, packages/core, packages/themes, apps/docs-site).
  • Stack: Vite + React 18 + TypeScript docs site; packages/core has no build step and is consumed as source.
  • Provenance: built iteratively by an AI coding assistant across ~14 documented waves, including cross-checks against shadcn/ui, Metronic, and a real "LendGuard" reference app. A "Manager Feedback" action plan exists and is only partially executed — several items are explicitly still open in the repo's own tracking file.
  • Scale: 21 component source files implementing ~50+ documented components; all visual styling lives in one 3,822-line components.css file (no per-component CSS split, no CSS-in-JS).
Verdict at a glance: the documentation describes a clean three-tier token pipeline and a fully token-driven component layer. In practice: two parallel, only partially-reconciled CSS variable systems; 236 raw hex literals despite a file-header comment claiming none exist; a broken out-of-the-box npm run dev; and a non-functional responsive navigation on the docs site itself below ~1024px.

Design System — Foundations

Colors

  • Primitive ramps: brand, secondary, tertiary, neutral (0–1000, 13 steps), success/warning/danger/info (50–950, 10 steps), 5 categorical accent hues (only 500/700 steps each).
  • Semantic layer covers bg, surface, text (primary/secondary/tertiary/disabled/inverse/onBrand), border, action.*, status.*, focus.ring — genuine, non-trivial light/dark divergence (e.g. hover state is brand.600 in light, brand.400 in dark).
  • FAIL A second semantic naming scheme was grafted on later (brand.text.*, brand.background.*, semantics.critical.*, …) that duplicates existing color.* tokens under new names with identical resolved values, rather than replacing them — packages/tokens/src/semantic.json:67-106.
  • PASS Disabled, focus, hover/active, status roles all have dedicated tokens and real consuming CSS.
  • PASS Dark mode is a genuine second value set (not a filter/invert trick), verified live with a working Light/Dark toggle.

Typography

  • 24 roles (h1–h6, text{32..12}{Regular,Medium,SemiBold,Bold}, eyebrow, numericData) each with explicit desktop/mobile size/weight/line-height/letter-spacing — more complete than a typical flat type scale.
  • Font: "Inclusive Sans" (base), "JetBrains Mono" (numeric/mono) — confirmed actually loaded and rendering live, not just declared.
  • FAIL typography.json does not reference primitives.json's own font.size.* scale — every role hardcodes its own px values instead of composing from the primitive tier one level down, so typography is architecturally a disconnected 4th token source, not a true semantic layer. typography.json:5 vs primitives.json:81-82

Spacing, Radius, Shadows, Breakpoints

  • Spacing: space.0–space.24, 13 steps, conventional 4px-based but non-linear at the high end.
  • Radius: 7-step scale (0/4/6/8/12/16/9999px) with real, working per-client theme overrides (clientb.json → sharp 2–6px, meridian.json → soft 10–22px) — PASS, structurally verified.
  • Shadows: 5-step elevation scale, confirmed to vary by component state (card interactive: none default → elevation.2 on hover) via live docs copy.
  • Breakpoints: 576/768/992/1200/1400px, deliberately matching Bootstrap 5's own scale (documented, not accidental).
  • FAIL The docs site's own live responsive behavior does not honor this scale for its primary navigation — see Responsive findings.

Reconciliation — DS ↔ Portal Integration Reality

The Portal does not consume the Design System package. A repo-wide grep for @core-ds in both main and journey-retirement returns zero matches — no import, no dependency in package.json, no CSS @import of anything under design-system-main/packages/.

What actually happened instead: specific token values were hand-copied. Example — the Design System's primitive brand-500 color is #1F4F8D (packages/tokens/src/primitives.json:5). The Portal's journey-retirement branch defines --theme-primitive-color-primary-500: #1F4F8D in its own, independently-authored src/styles/core-color-palette.css:39, with an inline comment noting where it is/isn't yet "applied." This is a manual, one-time value port from a Figma export or a design-system snapshot — not a build-time or run-time dependency. The Portal's main branch does not use this core-color-palette.css file at all; its tokens (--brand, --ink, --muted, etc.) are a separate, older hand-authored system in index.css.

Implication: every Design System fix in this report (button contrast, Tabs disabled state, token de-duplication, etc.) will have zero effect on the Portal unless someone manually re-transcribes the change — and conversely, the Portal's own component/CSS problems (4 parallel .btn definitions, 3 app-chrome implementations, no shared Table/Modal primitive) cannot be fixed "for free" by adopting the Design System, because nothing wires them together today.

Methodology & Evidence Notes

  • Scope: per explicit user direction, this audit covers the Design System ZIP and Portal branches main and journey-retirement (not design-system/saturna/cursor/token-audit-color-typo-a583/lendguard-chakra, which exist in the repo but were out of scope for this pass).
  • Method: the Design System ZIP was extracted to an isolated scratch location and run there; the Portal main branch was checked out into a separate git worktree; the journey-retirement branch was audited directly in the user's working directory, read-only, with a final git status confirming a clean tree at completion. No source file in any location was modified.
  • Live verification: all three targets were installed (npm install) and run with a live dev server on a dedicated port, then driven through a browser-automation tool across desktop (1440×900 or 1024×768), tablet (768×1024), and mobile (375×812) viewports, using accessibility-tree reads, text extraction, console/network capture, and screenshots.
  • Evidence discipline: every finding above is tagged PASS/PARTIAL/FAIL/MISSING/NOT VERIFIED and backed by either a file:line reference or a described live observation. Claims from the repos' own documentation (README, CHANGELOG, PROJECT_NOTES, manager-feedback trackers) were treated as evidence of intent/history, not as ground truth, and were independently re-checked wherever feasible.
  • Screenshot evidence: screenshots were captured and visually inspected live during each audit session (inline to the auditing agent) but are not persisted as standalone image files alongside this report; visual/responsive findings above are the direct written record of those live observations. Any claim not backed by either a live capture or a code reference is explicitly marked NOT VERIFIED / NOT CAPTURED rather than asserted.
  • No fixes were applied. This report reflects the state of both repositories as of 2026-09-17; no application source code was modified, no branches were merged, and no functionality was intentionally changed in the course of producing it.
