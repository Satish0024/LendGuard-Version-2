### 1.2 Component API shape (DS)
Every component follows one consistent pattern: a typed variant/size prop union, a `cds-*` BEM-ish class root (`cds-btn`, `cds-btn--{variant}`, `cds-btn--{size}`), and composition rather than duplication:

- **`Button`** (`Button.tsx:3-33`): `variant`: `primary | secondary | tertiary | destructive | outline-primary | neutral | success | warning | info` (9 variants — portal implements 3, see §4). `size`: `sm | md | lg`. `loading` prop renders `…` and sets `aria-busy`. `disabled || loading` both disable the control.
- **`IconButton`** (`Button.tsx:38-56`): same variant/size union, plus `shape: square | circle`, and **requires** `aria-label` at the type level (`"aria-label": string`) — DS enforces accessible-name-on-icon-button at compile time.
- **`Link`** (`Button.tsx:61-74`): `disabled` prop that also removes `tabIndex` and sets `aria-disabled` rather than only styling.
- **`Modal`** (`Overlays.tsx:6-29`): `role="dialog" aria-modal="true" aria-labelledby`, focuses itself on open, Escape-to-close wired via `onKeyDown`, scrim click closes, content click `stopPropagation`.
- **`ConfirmDialog`** (`Overlays.tsx:32-46`): built on `Modal`, `danger` prop swaps the confirm button to `variant="destructive"` and label to "Delete".
- **`Drawer`** (`Overlays.tsx:49-∼130`): unifies "Drawer" and "Slideover" as one component via `actions` (header buttons) and `aside` (side summary panel) props, `side: left|right`, animated open (280ms), and a documented `CORE_OVERLAY_THEME` constant because it's portaled to `document.body` outside the app's theme root — **an explicit rule the portal's Slideover does not have any equivalent for** (see §3 accessibility/theming risk).
- **`Toggle` / `ToggleGroup`** (`ToggleInputs.tsx`): `aria-pressed`-based toggle buttons, `sm|md|lg`, generic `<T extends string>` typed `ToggleGroup` for icon/segmented control groups.

Full prop-level reading of `Calendar.tsx`, `Combobox.tsx`, `DataDisplay.tsx`, `FormControls.tsx`, `Navigation.tsx`, `Questionnaire.tsx`, `Attachment.tsx`, `Disclosure.tsx`, `HoverCard.tsx`, `Layout.tsx`, `Misc.tsx`, `Primitives.tsx`, `ToastManager.tsx` was not completed in this pass (time-boxed) — **flagged as a Phase-1 follow-up**, not invented. The component inventory in §4 marks these as "DS side unread — verify before build."

### 1.3 DS ambiguities / gaps observed
- `semantic.json` carries **two naming systems for the same roles** — dotted (`color.action.primary.bg`) and hyphen/dot-mixed aliases (`brand.background.primary-strong`, `neutral.text.subtleleast` — note the typo/no-hyphen `subtleleast`). Both resolve to the same primitive in `light`/`dark`, but it's undocumented (in the files read) which one is canonical for new consumers — the portal's own CSS (see §3) has independently copied the **second, alias-shaped** naming almost verbatim, suggesting the alias block was the one leaked/shared with the portal team previously.
- `typography.json` values for `h1`–`h6` and the `text*` scale overlap in px size (e.g. `h3.desktop.size = 24px` and `text24Bold.desktop.size = 24px` are identical) with no documented rule for when to use a semantic heading token (`h3`) vs. a raw size+weight token (`text24Bold`) — ambiguous for component authors, flagged rather than resolved.
- `component.json` defines `stepper.*`, `sidebar.*`, `promoCard.*` tokens implying dedicated Stepper/Sidebar/PromoCard components, but no `Stepper.tsx`, `Sidebar.tsx`, or `PromoCard.tsx` file exists under `packages/core/src/components/` — these tokens are either consumed inline elsewhere (unverified) or the components are missing from the extracted package. Flagged as "component.json token group without a matching component file."
- No `Table.tsx` or `Pagination.tsx` component file was found in `packages/core/src/components/`, despite the portal having heavy, repeated table implementations (Investments, PlanDetails, AccountSummary, Portfolio, Transactions) — this is a **major undefined-in-DS gap**: the reconciliation cannot recommend a "match DS Table" action for any portal table because no DS Table component exists in the extracted package (it may live in `DataDisplay.tsx`, which was not fully read — **verify in Phase 2 before concluding it is truly absent**).
- Breakpoints in `primitives.json` (`sm 576 / md 768 / lg 992 / xl 1200 / xxl 1400`) are Bootstrap-style breakpoints; the portal's actual breakpoint usage was not exhaustively grepped in this pass (see §3, flagged as partial).

### 2.2 Token layer already exists in the portal, independently
`src/styles/index.css:29-122` defines a **portal-native token system** that already mirrors DS semantic naming almost 1:1 in spelling, but diverges in values and derivation:
- Portal: `--theme-primitive-color-primary-{50..900}` derived via CSS `color-mix(in srgb, var(--brand) X%, white/black)` from a single `--brand` hex (`index.css:29-38`).
- DS: `color.brand.{50..950}` are hand-authored fixed ramp values in `primitives.json` (11 stops including 950, vs. portal's 10 stops with no 950).
- Portal alias layer `--brand-border-primary-default`, `--brand-text-primary-default`, `--neutral-text-subtle`, `--semantics-critical-text`, etc. (`index.css:76-122`) uses **near-identical dash-cased names** to DS `semantic.json`'s alias block (`brand.text.primary-default`, `neutral.text.subtle`, `semantics.critical.text`). This is strong evidence someone previously hand-transcribed a subset of the DS semantic token names into the portal without wiring them to the DS's actual color values — the naming convention was copied, the values were not.
- Portal status colors are literal hex, not DS-ramp-derived: `--theme-colors-green-600: #147a4c`, `--theme-colors-yellow-600: #8a5a12`, `--theme-colors-red-600: #c0392b`, `--theme-colors-teal-600: #0e7490` (`index.css:59-71`) vs. DS `success.600 = #178451`, `warning.600 = #C27A10`, `danger.600 = #B72E38` — **all four semantic hues differ from DS**, not just the brand hue (which is expected to differ, being client-themed).
- 35 additional raw hex literals found via `grep -rn "#[0-9a-fA-F]{6}"` across `src/pages`, `src/components`, `src/lib` outside the `:root` block — likely the chart-color / gradient / confetti stragglers `PROJECT_NOTES.md` §6 already flags as a known issue. Not enumerated file-by-file in this pass; Phase 2 should re-run this grep and classify each hit.
